Replay Dataset Tutorial

客户端如何实现测试数据集回放

这份教程说明一个完整闭环：客户端先支持按 URL 参数进入回放模式；测试人员从 Chrome DevTools 导出 HAR 或抓包数据；转换脚本把原始数据拆成客户端可读的回放目录；GitHub Issue 自动触发校验、提交数据，并返回可点击的 WebGL 测试链接。

一句话版本 客户端只认一个稳定协议：debug=1 打开回放，debugDataPath 指向测试数据目录，debugStart 决定从第几局开始。
1 客户端必须先实现回放入口和 API 替身，否则测试链接打不开真实局面。
2 数据可以来自自己游戏或竞品游戏的 HAR，需要转换成统一回放格式。
3 GitHub Actions 负责自动转换、校验、提交，并在 Issue 里返回链接。

1. 客户端需要先实现数据回放功能

数据平台只能返回链接，真正让链接生效的是客户端。客户端要在启动时识别调试参数，跳过正常服务端请求，把回放目录里的 JSON 按顺序喂给原有业务逻辑。

A

URL 参数入口

识别 debug=1、debugDataPath、debugStart、token。没有 debug 时走正常线上逻辑。

B

回放数据加载器

先读取 manifest.json，再按顺序加载 001.json、002.json。Editor 可以支持本地目录，WebGL 推荐 HTTP 目录。

C

API 替身

把原来请求服务器的入口改成“如果 debug 开启，就从回放队列取下一条响应”。业务层仍然收到和服务端一样的 spin 数据。

WebGL URL
解析参数debug=1
debugDataPath=...
初始化配置保存 token、起始局数、数据目录。
传给 Unity通过启动变量或 WebCallback 进入 C#。
进入回放模式正常服务器请求被替换。
Replay Loader
读取 manifest确认文件顺序、数量、分组信息。
跳到起点debugStart=10 就从第 10 个 bet 开始。
加载 JSON远端 raw URL 或本地 HTTP 文件。
维护游标每次 spin 消费一条或一组响应。
Game Logic
下注玩家点击 spin，流程不变。
拿响应API 层返回回放数据。
播放表现盘面、连消、免费旋转、中奖动画复现。
记录日志错误时输出文件名、entry、sid。
实现边界 回放功能应该只在开发、测试或带明确 debug 参数的环境开启。不要让生产用户无意中通过任意 URL 读取外部测试数据。

2. 如何拿到原始数据

原始数据通常来自浏览器网络请求。可以抓自己游戏的线上数据，也可以抓对标游戏的数据做表现对齐，但要注意权限、账号、隐私和内部合规要求。

Chrome DevTools 导出 HAR

  1. 打开游戏页面，按 F12 或右键选择 Inspect。
  2. 进入 Network 面板，勾选 Preserve log。
  3. 过滤 fetch / XHR，开始实际下注或触发你要看的玩法。
  4. 操作几局后，在 Network 列表右键选择 Save all as HAR with content。
  5. 把 .har 交给转换脚本，抽取 spin 请求或响应。

需要保留的信息

字段 用途
请求或响应 JSON 提取 data、dt.si 或直接 spin 对象。
sid / spin id 定位单局问题，错误报告里可以直接追到服务器回合。
rl / wp / ptbr 客户端盘面、中奖线、消除和补牌校验的核心字段。
st / nst / tb 判断新 bet、连消、免费旋转、续转链。
转换目标 HAR 不是客户端最终使用的格式。转换脚本要把 HAR 里的有效 spin 数据提取出来，转成每行一个 JSON 的 capture 文件，或直接拆成回放目录。

3. 转成客户端可回放的数据格式

推荐使用“目录回放”格式：一个批次目录代表一次上传，一个 bet 或一组连续响应写成一个 JSON 文件，客户端通过 manifest.json 获取顺序。

1

001.json 等回放文件

保存客户端要消费的服务端响应。Mahjong 类数据一般按“实际扣费 bet”拆分，连消和免费旋转续转保留在同一组。

2

analysis.md

给人看的摘要：重点测试回合、Big/Mega/Super Win、连消、多线中奖、Scatter/FreeSpin、金色符号等。

3

validation_summary.json

给机器看的校验结果。GitHub Actions 只读这个 JSON 决定是否允许提交，不解析 Markdown。

4. 通过 GitHub Issue 自动处理并返回测试链接

GitHub 仓库负责把“上传数据”变成“可点击测试链接”。当前仓库的实现思路是：Issue 标题决定走哪个 workflow，Issue 正文附件提供数据源，Action 处理成功后提交批次目录，再把 url.txt 评论回 Issue。

5. 错误检查和失败返回

自动化平台不能只负责生成链接，还要防止坏数据进入主回放目录。当前 Mahjong 流程会把高危错误写入 validation_summary.json，Action 根据 has_errors 决定是否阻断提交。

通过

has_errors=false

提交 mahjong1date/ 或 mahjong2date/ 批次目录，更新 README 导航，在 Issue 评论中返回可用 raw URL 和 WebGL 回放链接。

校验结果
读取 validation_summary.json
阻断

has_errors=true

不执行 commit/push，只把错误数量、首个问题、文件、entry、sid、错误类型和说明写回 Issue，避免坏数据污染测试链接。

错误码 含义 为什么要阻断
WP_WAYS_MISMATCH wp 和当前 rl 盘面推导出的 Ways 中奖位置不一致。 客户端消除位置会和服务端数据不一致，动画和结算都可能错。
NEXT_RL_RESTORE_MISMATCH 上一条消除、金色转 Wild、当前 rs.rns 不能还原下一条 rl。 连消补牌后客户端盘面可能和服务端不同步。
TRUNCATED_CONTINUE_STATE bet 文件最后一条仍是继续状态，但没有下一条数据。 客户端会继续请求下一条响应，回放队列已经没数据。
失败时为什么没有可用 raw 链接 因为失败批次不会 push 到 GitHub。目录没有提交时，debugDataPath 指向 GitHub raw 会 404。需要本地复现时，先在本地生成目录，再用本地 HTTP 服务把 debugDataPath 指向本机地址。

6. 最小验收清单

这个流程是否真正可用，可以用下面清单验收。不要只看 Action 成功，要确认客户端能消费数据并复现表现。

URL 参数生效 debug=1 后客户端进入回放模式；去掉 debug 后恢复正常联网请求。
manifest 可访问 浏览器打开 {debugDataPath}/manifest.json 返回 200，不是 404 或跨域失败。
debugStart 可跳转 debugStart=20 能直接从第 20 个回放文件开始，方便定位单局问题。
重点回合可复现 Big/Mega/Super Win、连消、FreeSpin、金色符号等重点样本可以按 analysis 推荐链接打开。
错误数据被阻断 人为构造 validation_summary.has_errors=true 的数据时，Action 不提交目录，只评论错误摘要。
Issue 状态可流转 成功后自动打 待修复 标签；开发回复“程序已修复”，测试回复“测试已经验证”。
推荐落地顺序 先让客户端支持本地目录回放，再接入远端 raw URL；先跑一条最小 JSON，再跑真实 HAR 转换后的批量数据；最后把 GitHub Issue 自动化接进团队流程。
